# 클릭 입력 실험 기록 · 제품 기능 아님

## 확인된 사실

일반 권한에서 SendInput이나 mouse_event가 성공 값을 돌려줘도 게임 UI가 반응하지 않는 사례가 있었습니다. 실제 GetCursorPos가 목표에 도달하지 않거나 포커스/권한이 맞지 않으면 클릭 성공으로 간주하지 않았습니다. 사용자 직접 클릭은 해당 창을 닫았습니다.

게임이 관리자 권한이고 도우미는 일반 권한인 차이가 관찰됐습니다. 이후 제한된 관리자 테스트에서 현재 게임의 채팅 영역에 SetCursorPos → 즉시 위치 검증 → 120ms 누름/놓음을 보내 채팅을 여는 성공 사례가 있었습니다. Windows의 입력 권한 제약은 [Microsoft SendInput 문서](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)를 참고합니다.

클릭 전에 100ms 기다리는 동안 커서가 달라져 취소된 사례도 있습니다. 게임 자체 보정인지 실제 마우스 이동인지 확정하지 않았습니다. 하나의 고정 크기 성공을 전체화면/반쪽/세로 화면 모두 지원한다고 부르지 않습니다.

## 좌표와 권한의 구분

- screen 좌표, 게임 client 좌표, 다중 모니터의 음수 원점, DPI 배율을 구분해야 함.
- 게임 창을 옮기면 client→screen 변환을 다시 해야 함.
- 화면 크기/비율이 바뀌면 UI가 재배치되므로 비율 좌표만으로 모든 버튼을 찾을 수 없음.
- 게임이 가려짐/최소화/다른 창 적중이면 입력 취소가 필요함.
- 관리자 도우미를 고정 작업으로 실행하면 매번 UAC를 요구하지 않을 수 있지만 최초 승인은 필요하고 UAC 전체 해제와 다름.

## ATK와 key_macro 분석의 한계

ATK에서 M1은 단순 XButton이 아니라 왼쪽 버튼과 Space 등의 500ms 누름/놓음 반복 매크로였습니다. `injected=False` 관찰만으로 펌웨어에 내장됐다고 확정할 수 없습니다. 마우스 펌웨어·드라이버·소프트웨어 경로를 완전히 분리 검증하지 못했습니다.

`key_macro.exe`는 정적 분석에서 mouse_event/keybd_event/SetCursorPos 등의 가져오기가 확인됐지만 실제 성공의 단일 원인을 확정하지 않았습니다. 실행 파일은 저장소에 포함하지 않습니다. 사용자 하드웨어 방식을 새로 복제한 결과물도 없습니다.

## 현재 범위

`diagnostics/InputPrivilegeProbe.cs`와 `MouseInputMonitor.cs`는 개발 분석용 원본입니다. 자동 실행 경로에 연결하지 않았으며 마우스 관찰 기록은 개인 파일로만 보관합니다. 키보드 수집/게임 자동 입력 도구로 확장하지 않습니다. 게임 확인창 자동 클릭, 무인 무한 재개, 보안·동의 확인 대체는 구현하지 않습니다.

이 패키지는 Computer Use에 의존하지 않습니다. 사용자 입력 비교 실험을 다시 할 경우에는 목적·대상 창·한 번의 입력 범위를 별도로 확인해야 합니다.
